### 2.3 差异清单（按影响排序）

1. **密度差距是内容量差距，不是图框机制差距**。参考 A3 页 78–183 器件 vs 我们 6–24 器件；
   即使图框机制完全对齐，绝对密度也不可能相同。**参考工程的「密度」不可作为我们的验收基线**，
   只能作为观感参照（这一点 j1 的 A3 默认结论方向正确，但用「参考约 50%+」当目标值会误导）。
2. **尾页稀疏是真实缺陷**（t2 代码）：CLK 页 1 个模块、6 器件，实测 7.0%（自报）/ 8.7%（我量）。
3. **标题栏信息量不足**：缺 logo、Part Number、Schematic 名、Drawn/Reviewed 英文格；
   我们多出「图号/单位/批准」等中文格。属内容差异，非机制差异。
4. **模块框线型**：我们虚线，参考实线；且我们模块名在框内，参考在框外上方。
5. **多模块页页名**：`pageModuleTitle` 只在「本页所有 cell 同属一个模块」时用模块名，
   多模块页回落到工作表名（MAIN）/续表名。验收标准「页名=模块名」对多模块页不成立，
   需要明确：是接受回落命名，还是强制「一页一模块」。
6. **颜色**：参考边框 #A00；我们的边框色未取权威值——纯观感差异，但应在下一轮截图对照中固定。

### 2.4 我无法核验的项

- **参考侧「分区数量」自相矛盾**：参考 CORE 截图的属性面板显示 `X轴分区数量 1 / Y轴分区数量 1`，
  但画面上渲染的是 1–6 / A–D 六个分区。面板顶部同时显示 `选中数量 0`，说明该面板展示的是
  **页面默认属性**而不是图框符号的选中属性，因此**不能**用它证明「参考图框的分区数量」。
  要判定分区几何，必须读图框符号自身的源码。
- **参考侧器件的实际坐标**：`reference/index.json` 只提交了计数（components/rects/texts），
  `bbox` 与 `fillRatio` 均为 `null`，页面源码未提交 → 无法用 IR 口径复算（见 §4.4）。
- **Dpx/DRC 的原始返回**：我只看到 `drcStrict: "true"` / `drcUi: "[]"` 两个字符串，
  没有原始调用记录，无法独立复现。

## 3. ③ 对「原生图框不可行」结论的对抗性审查

先给结论：**我不推翻「在 V4.1.78 上，自绘图框是当前唯一可用交付」这一工程判断，但它被写成了
超出证据范围的普遍否定，且缺少两个决定性对照实验。** 逐条：

| # | 文档表述 | 我的审查意见 |
|---|---|---|
| 1 | §11.10/§11.11「没有任何受支持的方式把它装进 API 导入或 API 建页的工程」「只能由客户端 UI 创建」 | **夸大**。这是从单一客户端版本（V4.1.78）、单一发射策略（把 frame 写成 COMPONENT+ATTR）、且**无对照实验**推出的全称否定。§12.3 自己又说这些常量「供客户端后续版本支持时重新接线」，与无条件的「不可能」自相矛盾。应降级为「当前版本、当前发射方式下不可行」。 |
| 2 | §11.10.3「图框元件存在但 `componentType` 不是 sheet」 | **这是最可疑的一条，却被当成失败证据**。`componentType` 不是 sheet，恰恰说明**我们发出的源码没被识别为图纸符号**——这是发射缺陷的症状，不是平台能力的反证。要证明平台不接受，必须做对照：把**参考工程自己的页面源码**原样回灌一个新工程，看它是否渲染。该实验缺失。 |
| 3 | §11.10.4「`modifySchematicPageTitleBlock` 只能改已有图框」，依据是在 `titleBlockData={}` 的页面上抛 `TypeError: Cannot convert undefined or null to object` | **不构成因果**。同一现象同样可由「调用签名/参数结构不对」解释。文档没有给出「该调用在**参考工程已有图框的页面**上成功」的记录；若在参考页上也抛错，则结论应是「调用方式未知」而非「只能改已有图框」。缺对照实验。 |
| 4 | §11.9 提到 `sch_PrimitiveComponent.create` 会挂起 20s，故绕开 | **遗漏风险**。挂起 ≠ 失败；这是唯一为「放置元件」设计的 API，操作可能在超时后仍然生效。整个否证链从未走完这条路径。 |
| 5 | §11.10「页面里不会留下无效元件」（好处） | **未评估代价**：`titleBlockData` 恒为 `{}` 意味着平台侧任何依赖图纸元数据的功能（标题栏联动更新、打印/出图模板、BOM 的图纸字段）都读不到我们的标题栏值。这是**功能性缺口**，不是观感差异；验收标准「每页有且只有一套图框+标题栏」无法覆盖它。 |
| 6 | 未提及 | **双框风险**：参考截图属性面板存在「图纸」字段（我们的页面显示「无」）。若用户手动开启、或客户端后续版本自动补原生框，自绘图框会与原生框叠加。当前无任何检测/去重机制。 |
| 7 | 未提及 | **导出保真度未验证**：自绘 RECT/TEXT 在 PDF/打印/出图模板下的表现（线宽、颜色、是否被裁）没有证据，而原生框是平台一等公民。 |

**净结论**：把 §11.10 的标题从「否证」改为「本轮否证（版本/发射方式受限）」，
并补上 §3.2/§3.3 两个对照实验，才算证据闭环。当前证据足以支持「先发自绘框」的工程决策，
不足以支持「平台不可能」。

## 4. ④ `fillRatio=null` 的可核验替代量化口径

### 4.1 口径定义（已落盘、可复跑）

脚本：`docs/evidence/review/measure-fill.mjs`（纯 `node:zlib`，无第三方图像库）
结果：`docs/evidence/review/fill-measure.json`

1. 解码 PNG；把「页矩形」吸附到图框边框线（四边各做一次一维线搜索，窗口 ±12px）；
2. 内容区 = 页矩形内缩 4%（去掉双边框、分区刻度与 1–6/A–D 字），再挖掉右下角标题栏区（45%×22%）；
3. 内容包围盒 = 内容区内所有「非近白」像素（亮度 <200 或有彩度）的包围盒；
4. `fillRatio = 内容包围盒面积 / 页矩形面积`（与 `page-budget.spec.ts` 同口径：内容盒 ÷ 整页）。

### 4.2 结果

| 图 | 页矩形 | 内容盒 | **fillRatio** | 墨迹密度 |
|---|---|---|---|---|
| reference 00-CORE | 671×490（比例 1.369） | 587×434 | **0.775** | 0.128 |
| reference 01-POWER | 670×482（1.390） | 583×247 | **0.446** | 0.047 |
| reference 02-DEVICE | 671×482（1.392） | 618×370 | **0.707** | 0.107 |
| current t5-00-MAIN | 674×483（1.395） | 477×338 | **0.495** | 0.038 |
| current t5-01-CLK | 674×483（1.395） | 84×338 | **0.087** | 0.012 |

**自校验**：检测到的页矩形比例 1.369–1.395，A3 理论值 1.414（偏差 ≤3%，来自边框线吸附到内框
与 41% 缩放取整）；若吸附窗口放宽到 ±30px，会吸到工具栏线（比例变 1.32）——这个敏感性已在脚本注释中写明。

**与自报值的交叉验证**（这是本口径最大的价值）：

| 页 | t5 自报（IR 口径） | 我量（像素口径） | 比值 |
|---|---|---|---|
| MAIN | 40.7% | 49.5% | 1.22 |
| CLK | 7.0% | 8.7% | 1.24 |

两页比值稳定在 1.22–1.24：像素口径比 IR 口径系统性高约 23%，因为像素盒包含**模块框矩形与文字**
（IR 口径只取器件 ±60/±40 与导线端点）。**结论：自报的 40.7% / 7.0% 在量级与相对关系上被独立证实**
（MAIN 达标、CLK 严重不达标），同时给出了两口径之间的换算系数 ≈1.23（仅对我们的渲染器标定，
用于参考侧只能算指示性换算：参考 CORE 0.775/1.23 ≈ 63%，POWER ≈36%，DEVICE ≈57%）。

### 4.3 由已提交 `rectBox` 反推几何（不依赖截图）

`t5-index.json` 提交了 MAIN 的 4 个模块框：`x=260/580/900/1220, w=200, h=820`，页 A3 1655×1170。
按 `blocks.ts` 的常量（`FRAME_PAD=80`、`TITLE_HEADROOM=60`）反推：

- 模块框并集 = 1160×820 → 951,200 / 1,936,350 = **49.1%**（框口径）
- 成员盒（框内缩 80/80/60）= 1000×600 → **31.0%**
- 验收口径盒（成员 ±60/±40）≈ 1080×680 → **37.9%**（自报 40.7%，一致 ✓）
- CLK（1 个模块）= 160×680 → **5.6%**（自报 7.0%，一致 ✓）

**⇒ 自报填充率可信；CLK 尾页不达标是真实的。**

### 4.4 不能核验的部分

- **参考侧绝对填充率无法用 IR 口径复算**：页面源码/器件坐标未提交，只有计数。
  像素口径（§4.2）是替代口径，但它包含模块框与文字，与 IR 口径不可直接比较。
- **我无法核验参考侧的分区几何与标题栏格线坐标**（见 §2.4 第 1 条）。

### 4.5 对 t4「尾页再平衡 + 幅面收敛」的量化预测（请 j3 live 证伪）

用 §4.3 的同一模型 + t4 的实现常量（`FITTED_MARGIN=60`、`FITTED_OUTWARD_X/TOP/BOTTOM=180/200/140`、
`PAGE_EDGE_FRAMED=170`）推算**参考形状**的板（模块 200×820、单列窄模块）：

| 页 | 模块数 | 验收口径盒 | 计划页填充 | 收敛后页 | 收敛后填充 |
|---|---|---|---|---|---|
| 第 1 页 | 3 | 760×680 | 26.7% | 1230×1170 | **35.9%** ✓（勉强） |
| 尾页 | 2 | 440×680 | 15.5% | 910×1170 | **28.1%** ✗ |

原因可解释：这类模块成员盒高 600，收敛高度下界 = 600+340+230 = 1170，**正好等于 A3 高度**，
所以幅面收敛只能收窄宽度、无法压低高度，固定边距（左 60 + 右 170）在窄内容上占比过大。

**这与 t4 自己的夹具结论（A3 两页 45.4% / 40.9%）不一致**，因为 `page-budget.spec.ts` 的夹具
模块是「宽模块」，而参考工程的模块是「窄高模块」。**t4 的 ≥35% 结论只在自家夹具上成立，
对参考工程形状很可能不成立。** 该预测可用 j3 的 live 复测在一轮内证伪或证实，是我建议的下一道门禁。

## 5. 结论与残余风险

1. 门禁：**独立复跑全部通过**（tsc 0 / oxlint 0-0 / 542 用例 / 覆盖率 100）。
2. `current/` 证据**已过期**（t2 代码），不能作为当前实现的验收证据；需重新取证。
3. 同构性：**图框机制同构**（双边框 + 分区刻度 + 标题栏 + 模块框），
   **标题栏内容与模块框线型部分同构**，**密度不可比**（内容量差 3–7 倍）。
4. 原生图框结论：工程决策可接受，**全称否定不成立**，缺 2 个对照实验与 3 项风险（双框、导出保真、元数据功能缺口）。
5. 填充率：自报值经两条独立路径（像素量测、rectBox 反推）证实；
   **但 t4 的达标结论只覆盖自家夹具，参考形状的尾页按模型仍约 28%**。

## 7. 实测闭环（12:20，j3 交付两份输入后补测；覆盖 §2.4 未决项与 §4.5 预测）

### 7.1 §2.4 未决项已解决（我自己在提交的 index.json 里核对）
- 参考 A3 页（CORE/POWER/DEVICE）的 `titleBlockData` **只有文本字段**（`Symbol=Sheet-Symbol_A3`、`Page Size=A3`、`@Page Name`…），没有 `Width`/`Height`/`X Region Count`/`Y Region Count`/`Border`/`Title Block`。
- 只有 A4 绘图页（P1）才有这些字段（`Width 1170`/`Height 825`/`X Region Count 6`/`Y Region Count 4`/`Border 1`/`Title Block 1`），且 `Symbol=Drawing-Symbol_A4`。
- ⇒ 面板那组「分区数量/图纸宽高/边框/明细表」是 **Drawing-Symbol_*（绘图页符号）** 的参数；A3 原理图页上显示 1/1 是**未选中符号时的回退值**，不是图框参数。画面上的 1–6/A–D 是 `Sheet-Symbol_A3` 符号内部画好的图形，不可参数化。
- 我撤回 §2.4 的「无法核验」；同时这也意味着**我们自绘的 6×4 分区刻度只能仿形**，不可能与参考共享参数。

### 7.2 复现陷阱（影响所有基于 lib/ 的测量）
`packages/*/lib/index.js` 由 **tsdown** 产出，`tsc -b` 只写 `lib/types`。所以直接 `node docs/evidence/tools/t5-board.mjs`（它 import 的是 `lib/`）若没先 `pnpm build`，读到的是**旧 bundle**：我第一次跑得到 4+1 页（37.9%/4.2%），正是因为 lib 时间 11:47 < layout.ts 12:00，且该 bundle 里 **0 个 t4 标记**。建议证据脚本改为从 `src` 跑（vitest），或在脚本里断言 bundle 含 t4 标记。

### 7.3 t5 形状的真实结果（当前 src 树，vitest 直跑，脚本见 `t6-board-probe.spec.ts`）
| 页 | 器件 | 模块 | 交付幅面 | 填充 | 页名 |
|---|---|---|---|---|---|
| 0 | 18 | 3 | **1230×1170**（收敛） | **35.9%** ✓ | MAIN |
| 1 | 12 | 2 | **910×1170**（收敛） | **28.1%** ✗ | MAIN 2 |

- 再平衡与幅面收敛**确实生效**（4+1 → 3+2，两页都收敛），0 越界、0 压标题栏。
- **尾页 28.1% < 35%**，与 §4.5 的解析预测（35.9% / 28.1%）逐位吻合。
- 页名是 `MAIN` / `MAIN 2`，**不是模块名** → 验收项「页名=模块名」不成立。

### 7.4 为什么 35% 在这个形状上不可达（量化证明）
尾页 2 个模块：tight 盒 440×680 = 299,200；outward 宽 680 → 收敛宽 = 680+60+170 = **910**；高 = min(1170, 600+340+230) = **1170（被 A3 高度卡住）**。
要在 910 宽下达到 35%，高度须 ≤ 299,200/(0.35×910) = **939**；而内容高度下界 = 600+340 = 940，再加 230 边距即 1170。**高度方向无收敛空间，宽度方向已到 910 下界。**
⇒ 在 clearance 24（edgePad 170）+ margin 60 前提下，**2 模块尾页的填充上限 ≈ 28%**，35% 不可达；全页加权平均也只有 32.6%。
可选项：(a) 验收改为「尾页 ≥28% + 本证明」或「页面均值 ≥32.6%」；(b) 放宽尾页 edgePad —— 违反 clearance 24，不可接受；(c) 减模块 —— 由内容决定，不可行。

### 7.5 修订后的结论
- **t4 的再平衡+收敛真实生效**（尾页 4.2% → 28.1%），但「每页 ≥35%」在参考形状上**不可达**，属结构性上限而非实现缺陷；t4 报告里「A3 两页 45.4%/40.9%」只在自家宽模块夹具成立。
- 对 t4 的独立判定由 partial 改为 **fail**（验收未达成，尽管改进真实且上限已量化证明）。
